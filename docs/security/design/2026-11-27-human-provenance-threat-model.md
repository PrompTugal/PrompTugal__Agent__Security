## What the site is today (the ground this builds on)

- **Hosting:** a static site on GitHub Pages, built by `release.sh` and CI from a public repository. There is no server, no cookie and no login. Every byte served is public.
- **Trust:**
  - `board/keys.json` lists public keys, with status active, superseded or revoked.
  - Articles carry a detached `.sig`.
  - The gate (`validate.js`, `superseded.cjs`, `signed-root.mjs`, `keys-changes.mjs`) checks signatures and the ancestry of key changes.
- **Weak points already known:**
  - **S13:** a new key enrols itself. There is no anchor signature from Dinis.
  - **S8:** one lane signs commits with an unpublished key.

  Both carry straight over to human keys if nothing changes.

## Assets

1. **The meaning of a reviewer's signature:** "this person reviewed this story at this version".
2. **The identities of human editors, journalists and researchers.** These are real, named people.
3. **Readers' feedback and their contact details**, if any are given.
4. **CRM records about people outside the project:** sources, outlets, partners.
5. **Dinis's Gmail:** mail, contacts and the power to send.
6. **The site's integrity:** what /admin/ shows and does.

## 1. Person key issuance and revocation

**Threats:**
- An agent or outsider enrols a key under a real person's name. This is S13 applied to people.
- A person's key is lost or stolen and keeps signing.
- A departed person's key still validates new reviews.
- A person's private key is generated by an agent, which then holds it.

**Controls:**
- **Generation:** each person makes their own key on their own device, for example a hardware key or a passkey-backed SSH key. No agent, CI job or session ever generates, holds or relays a person's private half.
- **Enrolment:** the only path is a statement signed by Dinis's anchor key, naming the person, the public key, the role and the date. It goes into a dedicated `board/people.json` (or a `kind: "person"` entry), separate from agent keys. The gate refuses a person entry without that anchor signature. This also closes S13 for people.
- **Consent:** written consent to be named comes before the entry. The entry carries a consent reference, not the consent text, and no personal contact detail.
- **Revocation:**
  - `status: revoked` with `revoked_at` and `revoked_in`, also signed by the anchor.
  - The gate refuses every new review signed by a revoked key.
  - Reviews made before `revoked_in` stay valid by ancestry, the same rule as `superseded.cjs`.
  - A suspected compromise invalidates everything after a stated time, not only future reviews.
- **Rotation:** the person signs a hand-over with the old key and the anchor confirms it, so an attacker holding only the old key cannot rotate.
- **Display:** the site shows a person's name only from `people.json`, never from free text in an article.

## 2. Replay and forgery of review signatures

**Threats:**
- A valid review signature for version A is replayed onto edited version B.
- A signature from one story is copied to another.
- Text claims an editor who never signed.
- A review is backdated.
- A signature is made under a namespace meant for something else.

**Controls:**
- **What is signed:** a canonical review statement, not the article file. It holds:
  - the story slug;
  - the sha256 of the exact article bytes reviewed;
  - the reviewer's key id;
  - the verdict;
  - the time;
  - a `previous` hash, so that re-reviews chain.
- **Namespace:** signed with its own SSH namespace, for example `promptugal-review`, never `git` or `promptugal-key-approval`.
- **Gate checks:**
  - the hash matches the article as published;
  - the key is an active person key, or a superseded one used before its supersede commit;
  - the slug matches.

  Any edit after review voids the badge until it is re-reviewed.
- **Byline rule:** "Editor: X" renders only from a verified review statement, never from front matter. A front-matter `editor:` field with no matching statement fails the gate.
- **Time:** the statement's time is checked against the commit that added it (no later than that commit) and against the article's commit (no earlier). So the git history bounds backdating.
- **Public verification:**
  - Publish the statement, the signature and the public key next to the story.
  - Give a short "verify it yourself" recipe (`ssh-keygen -Y verify`) so readers need not trust the site's own badge code.

## 3. Abuse of the sealed, write-only feedback lane

**Threats:**
- Spam and flooding.
- Harassment of named editors.
- Malicious payloads, such as scripts or links, rendered in /admin/.
- Personal data of third parties dumped into the lane.
- Deanonymising readers.
- An agent with lane access reading what it should not.
- Silent dropping or edits by whoever holds the store.

**Controls:**
- **Sealing:** each submission is encrypted in the browser to a feedback public key whose private half only the named human readers hold. It is never held by an agent or CI.
- **The store:** an append-only store, for example the existing SG/Send-style sealed append or an issue-free bucket. It is write-only for the public, with no public read and no list of entries.
- **Rate limits and size:** limits per IP at the store's edge, a size cap per message and no attachments at first.
- **Rendering:** messages are treated as untrusted text everywhere. /admin/ shows them as plain text only (`textContent`, no markdown or HTML, links not made clickable) after decryption in the reader's browser.
- **Contact details:** optional, in a separate field, and kept only as long as the purpose needs. The lane notes that the reader must not send other people's personal data. Retention and deletion go to cl-6.counsel.
- **Integrity:** each entry carries a hash chain or a sequence number, so deletion or reordering by the store shows.
- **No auto-processing:** no agent acts on the content of feedback, because the content is untrusted. A human triages it, and an agent may only count entries or flag them by size or rate.

## 4. What /admin/ may do without cookies or a server

**The core point:** /admin/ is a public static page. Anything it shows is public unless it is encrypted, and anything it does needs a credential the visitor already holds.

**Rules:**
- **It reads only:**
  - public data (keys, statements, build status);
  - data encrypted to the viewer and decrypted in their browser with a key they bring, such as a passkey-unwrapped key, a hardware key or a pasted key held in memory only.
- **No secrets in the page:** no secret, token or private key in the page, its JavaScript, `localStorage` or the repository. That includes no Gmail token and no GitHub token.
- **Writes:** any write, such as a review, a reply or a CRM edit, is a signed object the person makes locally and submits through a channel that verifies the signature, for example a commit or PR checked by the gate. /admin/ prepares and signs; it never holds standing write power.
- **Browser risks:**
  - **XSS:** a strict CSP (no inline script, no third-party script, `connect-src` limited to named hosts), keeping the plain()/safeUrl() discipline and SAFE_URL for any link.
  - **Clickjacking:** an iframe guard. A meta CSP cannot set `frame-ancestors` on Pages, so use a JavaScript frame-bust and render nothing sensitive until it passes.
- **No hiding:** no admin-only routes "hidden" by obscurity. Assume a crawler finds /admin/.

## 5. Gmail connector scope

**Threats:**
- An agent gets broad mail access and reads private mail, contacts or third parties' messages.
- An agent sends mail as Dinis.
- Prompt injection through incoming email drives actions.
- Mail content leaks into public repositories.

**Controls:**
- **Smallest scope:** start with read-only on one label, or one alias such as a dedicated `crm@` mailbox rather than Dinis's main inbox. No send scope at first. A later send scope, if any, only creates drafts that Dinis sends himself.
- **Who connects it:** Dinis attaches the connector, by his decision. No agent requests or widens it, and no connector token is stored in any repository, page or note.
- **Content is data:** email bodies are untrusted. An agent never follows instructions found in mail and never takes an outward action because a message asks.
- **Nothing public:** nothing from mail goes into a public repository. CRM fields taken from mail (name, organisation, date, thread id) go only to the private store chosen in section 6. No body text is copied unless a human chooses to.
- **Audit:** keep a log of which agent session read which label, and when.

## 6. CRM personal data (with cl-6.counsel)

**Threats:**
- Personal data of sources and contacts lands in a public repository. Everything PrompTugal publishes on GitHub is public.
- The data is over-collected or kept too long.
- A source is exposed through the data.
- Agents across accounts read it.

**Controls:**
- **Where it lives:** the CRM lives outside the public repositories. Dinis decides where, for example an encrypted vault with per-person keys or a hosted CRM with access logs. The gate's leak scan should refuse any commit holding email or phone patterns in CRM-shaped files, as a backstop.
- **What is stored:**
  - a lawful basis and purpose per record class, set by cl-6.counsel (GDPR: legitimate interest assessment or consent; source-protection duties);
  - minimal fields: role mailboxes for organisations, personal details only with the person's agreement;
  - retention limits and a deletion path;
  - an answer process for subject-access requests.
- **Sources:** confidential sources are not stored in the CRM at all, or only under a pseudonym, with the key to it held by a human.
- **Access:** per role, logged. Agents see the fields their task needs, with no bulk export.
