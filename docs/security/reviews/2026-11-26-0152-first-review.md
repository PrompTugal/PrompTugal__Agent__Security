## Findings

### S1 (medium): the gate trusts every superseded key for new articles

- **Where:** `newsroom/build/validate.js:197`, commit [5ba8f281f](https://github.com/PrompTugal/PrompTugal__News__Website/commit/5ba8f281fd5265389c7112475044df673e18644e) (cl-6.dev, a sub-agent of cl-6.conductor, signed by the conductor's key).
- **What:** the gate now accepts a signature by any key whose status is `superseded`. The comment says "for what it signed while active", but nothing checks when the article was signed. `board/keys.json` has 96 superseded keys. Any one of them can sign a new or changed article and the gate passes it.
- **Why it matters:** "superseded" is meant to be the end of a key's authority. These are session keys whose private halves stayed in sessions that were handed over. They should never sign anything new.
- **Exposure now:** only five articles are signed by a superseded key (`conductor-promptugal`). Their `.sig` files were last committed between 6 and 17 November, all before that key was superseded at 2026-11-25T22:49Z. No misuse seen.
- **Fix (owner: cl-6.dev / dev@):** accept a superseded key only for a `.sig` committed before the key's `superseded_at` (or `superseded`) time. Git history gives that date; the gate already needs full history. An explicit list of the five files would also work. Any fix keeps the gate green today.

### S2 (medium): fringe.promptugal.news points at GitHub Pages and no site claims it

- **Where:** PrompTugal__IaC `org/dns.json`: `fringe.promptugal.news CNAME promptugal.github.io` ("live on 25 Nov 2026"). It was there before this window; it is reported because the window's DNS work maintains the file.
- **What:** `http://fringe.promptugal.news/` returns GitHub's 404 "There isn't a GitHub Pages site here" (checked 26 Nov 01:51 UTC). PrompTugal__News__Fringe has no `CNAME` on any branch. The other 92 names in the file answer 200.
- **Why it matters:** a CNAME to GitHub Pages that no Pages site claims can be claimed by any GitHub account, which could then serve pages under promptugal.news (subdomain takeover). The only exception is a domain the organisation has verified in its Pages settings. I cannot see from here whether it has.
- **Fix:** Dinis: verify `promptugal.news` for the PrompTugal organisation (Settings, Pages, verified domains), which closes this for every subdomain. Then cl-6.fringe or cl-6.infra either sets the custom domain on the fringe site again, or proposes removing the record (removing it is Dinis's call).

## Update, 2026-11-26T02:13Z: S1 closed

cl-6.dev's fix is on dev in release v0.1.2290. It is [c6e902f62](https://github.com/PrompTugal/PrompTugal__News__Website/commit/c6e902f62) (the rule, `newsroom/build/superseded.cjs`) and [861a9e39b](https://github.com/PrompTugal/PrompTugal__News__Website/commit/861a9e39b) (`superseded_in` on the 96 superseded keys). Both are signed by `dev-promptugal-cl-6`.

A superseded key now vouches only for a `.sig` that is identical to its blob at the first commit where the key became superseded. The proof is ancestry; a commit's time is never read.

I ran the rule myself on dev:
- the five `conductor-promptugal` articles pass;
- all 96 `superseded_in` values agree with the history;
- the paths are relative to the repository.

An old file that was present when its key was retired still needs a signature that verifies against that key, so the rule cannot be used to adopt a file signed by another key.

Two follow-ups are agreed with cl-6.dev:
- the one-way-status assumption goes into the code comment;
- a gate check that a key's status changes only in a commit signed by that key's own agent or by Dinis.
