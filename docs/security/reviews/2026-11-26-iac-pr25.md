## Changes needed (blocking)

- **B1. The merge can launder unchecked commits into the anchor.**
  - `merge` uses `merge_method: rebase` with `sha=` pinned to the PR head, but nothing pins the PR's base. The anchor becomes the merge, so every commit already on `dev` between the last verified run and the merge becomes an ancestor of A and is never checked.
  - Example: before the dev-gate ruleset exists, anyone with push can land a commit that changes `pages.yml` or a check script. The bootstrap merge then blesses it.
  - **Fix:** before merging, require the PR's `base.sha` to equal `dev`'s head, and `dev`'s head to equal the last verified anchor. That anchor is found exactly as `pages.yml` finds it: the latest successful push run of `pages.yml` on `dev` whose `checks` job passed. After merging, require the merged commit's tree to equal the approved head's tree before the anchor is set. Refuse otherwise.
- **B2. The `pages.yml` block is checked by content, not by position.**
  - `checkPagesPatch` accepts the two pinned lines anywhere. With the `fi` placed after the lines that run `check-signatures.mjs`, `leak-scan.mjs` and the rest, setting the variable would skip every check.
  - **Fix:** the lines between the added `if` and `fi` must be exactly the existing anchor lookup (pin its text or its hash per repository). The line after `fi` must be the existing `[ -n "$A" ] || ...` check.
- **B3. One key format cannot fit every repository.**
  - `homeKeyOf` reads only `ssh_ed25519`, and `checkKeys` requires `ssh_public_key` to start `ssh-ed25519`. News__Signals' `check-signatures.mjs` reads `git_signing.pem` (P-256, PKCS8), and my ruling for cl-6.signals was the P-256 entry. As written, Signals can never pass.
  - **Fix:** a per-repository `key_format` in the policy:
    - `ssh_public_key`/ed25519 against the home's `ssh_ed25519`;
    - `git_signing.pem`/P-256 against the home's `ssh` (compare the converted key, not the text).
  - Signals' leak-scan patch (`0001`) also has to be listed under `gate_changes` for News__Signals, with its sha256.
- **B4. The gate paths are too narrow.**
  - `scripts/check-*.mjs` misses Signals' `scripts/check-signatures-trusted.sh`, every repository's `scripts/leak-scan.mjs`, Travel's `scripts/commit-exemptions.json`, and a root `.gitattributes`. Each is part of a gate or changes how one reads files.
  - **Fix:** use `.github/**`, `scripts/check-*`, `scripts/leak-scan.*`, `scripts/commit-exemptions.json`, `team/**` and `.gitattributes`. Better still, take the list from the files each `pages.yml` copies from A.
- **B5. The gate status on `dev` looks at the head commit only.**
  - `gate-status.mjs` reads `commits/{sha}` for `dev`, so a push of several commits hides a gate change in any commit but the last.
  - Both the commit and the compare APIs cut their file list at 300, so a large push can push a gate file out of view.
  - **Fix:** for `dev`, compare from the last commit that holds a success status (or the anchor) to the head. On any branch, fail closed when the list holds 300 files or the API says it was cut.
- **B6. The App bypasses the dev-gate ruleset.**
  - `bypass_actors` holds the Integration (5777442) with `always`, so every App action can push to `dev` without the status, Org apply included.
  - The bypass is not needed: the approved head can carry the gate status, because I sign `approvals/gate/<repo>/<head_sha>.json` with the key-bootstrap approval, and the merge then goes through the pull request as for anyone.
  - **Fix:** remove the Integration bypass and keep organisation admins (Dinis, for escalations).
- **B7. The workflow takes the action repository from stdout.**
  - `plan` prints each item's errors, which include file names from the pull request, which an attacker controls. A name with a newline can print its own `action_repo=` line, and that value goes into `$GITHUB_OUTPUT`.
  - **Fix:** read the repository from `plan.json` and check that it is in `policy.repositories` before minting a token. Never print raw file names; quote or escape them.
